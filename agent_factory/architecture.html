The Agent Factory

A label-driven autonomous pipeline that triages GitHub issues, dispatches coding agents into git worktrees, gates their work deterministically, publishes reviewed pull requests, and lands them through a serialized merge stage — a human can hold any merge by pulling the factory-approved label.

Diagram A — system architecture

Nine components, twelve directed edges. GitHub on the left, the controller in the center, the per-ticket workbench on the right.

Diagram B — ticket lifecycle

One ticket, start to terminal: triage decision, worker attempts under the gate, one codex bounce, then the merge stage or escalation.

factory gate

The gate's checks

  • conflict markers — git grep for the seven-char markers
  • every [[gate.check]] from .factory.toml, in order (e.g. lint, tests, smoke)
  • leak scan of base..HEAD — internal / confidential / Jira-style terms
  • checks marked exclusive run under the host lock; every check has a [gate].timeout (default 1200 s)

factory dispatch

Budgets, escalation & the merge stage

  • MAX_ACTIVE=2 lock-held worktrees · MAX_ATTEMPTS=3 worker+gate rounds
  • 90-minute wall clock per ticket · 1 codex review bounce, then escalate
  • escalation = unassign + ready-for-human + comment with log path
  • codex APPROVE → factory-approved label on the PR
  • merge stage runs first each pass: squash-merges at most one PR that is factory-approved, green on CI, and whose head contains the current main tip
  • stale-but-approved PRs are rebased, re-gated on the host, force-pushed; a red CI run pulls the label and escalates once
  • a human holds any merge by removing factory-approved
