# Review: #79 B2 — source-versioned PR feedback

## Required fixes

### R1. Repository native ID from the full snapshot is never wired into the collector; an initial-head failure then discards every independently read item
- `factory/dashboard.py:812` declares `repo: dict = {}`, and `factory/dashboard.py:886` passes `repository={"id": repo.get("id"), ...}`, but nothing in the diff assigns `repo` from `data["repository"]`. The `id` added to the GraphQL query at `factory/dashboard.py:124` is dead; `repository.id` reaching `feedback.collect` is always `None`.
- The collector only learns the repository ID from the `pr` head read (`factory/feedback.py` `head()`, `repository['id'] = identity(repo['id'])`). `item()` then refuses any record when `not repository['id']` (`factory/feedback.py` `item()`, the `identity_missing` branch).
- Trigger: initial `HEAD_QUERY` read fails/times out/malformed while reviews, threads, and checks succeed. Impact: all review/thread items are dropped with `identity_missing`, even though the snapshot already holds the repository native ID (and the PR native ID is passed correctly). Checks are also skipped (`head_unavailable`), so the object has zero items despite readable sources.
- Rule: issue Scope — "When a PR is present but a feedback source cannot be read, return the schema-1 feedback object with explicit unavailable/partial coverage and retained independent facts"; schema `errors` — "One failed source must not discard usable independent sources."
- Fix: assign `repo = data["repository"]` in `snapshot()` (next to the existing `data = github()` block) so `repository.id` is populated from the full snapshot; `tests/test_feedback.py` should cover initial-head failure with `REPO["id"]` supplied and assert reviews/threads survive.

### R2. `producer.revision` can attribute a foreign repository's HEAD to the Factory source
- `factory/dashboard.py:875-878`: `source_root = Path(__file__).resolve().parent`, then `git rev-parse HEAD` and `git status --porcelain -- .` with `cwd=source_root`, with no check that `source_root` is tracked by that repository.
- Trigger: Factory installed into a venv that lives inside another git checkout (e.g. `uv sync` creating `.venv/` in the target project, which README documents as the source-checkout workflow). `rev-parse HEAD` returns the *target project's* HEAD; `.venv` is gitignored so `status --porcelain -- .` is empty → treated as clean → `revision` = an unrelated commit.
- Impact: schema rule "`revision` is a verifiable source/build revision when available, otherwise null" is violated with a false verifiable value; `observation_id` is unaffected, but the handoff to #15 relies on `producer.revision` as provenance.
- Fix: require the package directory to be tracked by that repo before trusting the SHA (e.g. `git ls-files --error-unmatch feedback.py` returning success, or `git rev-parse --show-toplevel` plus a tracked-path check); otherwise `None`. `[INFERENCE]` also confirm `sh()` does not raise when `source_root` is in no git repo at all (installed site-packages); if it does, every full snapshot with a PR ticket fails on installed hosts.

### R3. Exit gate 4 regression boundary for `--runtime-json` is not in the diff
- Exit gate 4 requires: "`factory dashboard --runtime-json` performs no feedback/GitHub read and its schema stays unchanged." The diff adds no assertion that `feedback.collect` / `dashboard.github` is not invoked on the runtime path (`tests/test_factory.py:2397-2449` only exercises `snapshot()`).
- The runtime path is not touched by the diff, so behavior is likely intact, but the acceptance criterion is a test boundary, not a behavior claim. If an existing runtime-json test already patches `dashboard.github` with a failing side effect, extend it with `mock.patch.object(feedback, "collect", side_effect=AssertionError)`; otherwise add that one assertion.

## Optional suggestions

- `factory/dashboard.py:216` replaces `proc.stderr.strip()` with the fixed `"GitHub read failed"`. The collector already sanitizes in `request()` (`factory/feedback.py`, fixed `source_unavailable`/`timeout` messages), so the full snapshot's existing `errors: ["github: ..."]` lost its operator diagnostic (auth failure, rate limit) for no feedback-safety gain. Keep stderr on the default-query path; sanitization belongs in `feedback.py` where it already is.
- `factory/dashboard.py:883-891`: the collector runs for every selected ticket with a PR, including merged/closed ones, costing ~6 `gh` subprocesses and up to 30 s each, sequentially. Issue says "Preserve full-snapshot cadence." Consider measuring on the target host; if cadence regresses, restricting collection to open PRs is the simplest bounded change (not requested, so optional).
- `factory/dashboard.py:150`: `headRefOid` added to the main PR query is unused (collector takes only `id/number/url`). Either drop it or pass it as expected-head evidence; dead query fields are maintenance noise.
- `factory/feedback.py` reviews loop: `updated=row.get('updated_at')` — the REST review object has `submitted_at`, not `updated_at` `[INFERENCE]`, so every review gets `source_updated_at: null` and any truncated review body always emits `change_detection_incomplete`. If `submitted_at` is acceptable as the provider time signal, use it; otherwise document that reviews have no update signal (README currently says this only for check runs).
- `factory/feedback.py` checks loop: `author=row.get('creator')` — check runs expose `app`, not `creator` `[INFERENCE]`; `author.login` will always be null for `check_run`. Harmless (unknown is valid) but attribution could be evidence-backed via `app.slug` as `bot`.
- `factory/dashboard.html:1047` `h('details', { open: expanded, ... })` with `expanded=false` in the Inbox: if `h` applies attributes via `setAttribute`, `open="false"` is truthy and every item renders expanded. `[INFERENCE]` — verify against the existing `h` helper; the smoke-proof browser check should show Inbox items collapsed.
- `factory/dashboard.html:1263-1277` and `factory/briefing.py:231-234`: wording changes to existing facts ("Legacy local gate failures", `pull_request_evidence_notice`) exceed the "task facts … presentation only" touch list. Not blocking, but they alter existing text consumers were reading; keep the minimum needed to mark legacy verdicts non-authoritative.
- `factory/briefing.py:385-387`: the coverage citation's cap is `CONTEXT_CAP - sum(sources)`, which is ≥1000 bytes only in the worst case; the feedback coverage notice (identity + coverage + errors JSON) is appended last in `notices`, so under a full context it is the part cut. Ordering is deliberate and reported, so acceptable; noting for the #15 consumer that coverage JSON may be absent from the briefing bundle.
