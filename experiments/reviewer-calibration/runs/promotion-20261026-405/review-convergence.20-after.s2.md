**The blocking defect: FIX can merge code that was never approved.** FIX pushes the worker's change before the review runs (`factory/manage.py:124`). It never removes an old `factory-approved` label from the PR. That label is still there when the escalation came from a conflicting rebase or a gate failure after rebase: `snapshot/factory/dispatch.py:722-729` escalates without removing it. The merge stage only checks for the label, green CI, an up-to-date head and no requested changes (`dispatch.py:803-808`); it doesn't check the issue's labels.

So for the `conflict` profile this diff adds: if the review returns REVISE, `manage.py:130` only escalates the issue. The pushed, rejected code then merges on a later pass once CI goes green. A related path: if the gate fails or the time budget runs out (`manage.py:121-123`), the worker's commits stay unpushed in the kept worktree. The merge stage then rebases them, re-gates and force-pushes them (`dispatch.py:720-731`), and they can merge under the old label.

This breaks a rule the diff states itself: "Only a fresh APPROVE restores `factory-approved`" (`README.md:99`). It also breaks `skills/factory/SKILL.md:108`, which says a merge needs `factory-approved`, and the rule in `docs/manager-plan.md:143` that the label is re-added only after gate PASS and a fresh APPROVE. The fix is one `gh pr edit --remove-label factory-approved` call in the FIX branch, before the worker runs. Nothing new needs adding.
