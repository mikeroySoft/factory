**Important finding (F1):** `manage.py:272` records the `manager_failed` escalate row before the human-takeover check at `manage.py:281`.
- **Trigger:** a human comments or relabels the ticket while a failing manager command is running. The check at line 281 sees the activity and skips the ticket without recording a `manage` event.
- **Next pass:** the newest escalate row is now the `manager_failed` row (same round, no `manage` event), so it's picked up again. `human_activity` only looks at timeline items newer than that row's `at` (`manage.py:136`), so the human's earlier action is ignored.
- **Impact:** the manager runs again on a ticket a human has taken. If it returns RETRY or ROUTE, `apply` removes `ready-for-human`, which breaks the guard the comment at `manage.py:280` exists for.
- **Before this diff:** no extra row was written, so the next pass re-checked from the original escalation and still saw the human.
- **Fix:** record the `manager_failed` row only after the takeover check passes, next to the `manage` record. Alternatively, skip `manager_failed` rows when choosing `escalation` at `manage.py:237`.
